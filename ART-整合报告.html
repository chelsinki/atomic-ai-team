摘要

本报告整合了围绕 Porsche CCP ART 重组的研究成果，形成一个 AI 原生交付的开放框架。核心主张：

将传统 5-9 人 Scrum Team 拆分为 3 人原子小队（AI Orchestrator + AI Engineer + Harness Master），通过 N 个 AI Agent 实现产出倍增。同样的人，做更多的事——增效不降本。铁三角 = PO → Dev → SM 的 AI 时代极简版。

框架的"内核"与"实例"：

层次 内容 变化频率
Core 框架内核（稳定） 三角色定位、人机协作哲学、组织演进方向、可扩展接口 年度级
Instance 实践实例（可替换） 具体周期长度、Squad 数量、工具选型、技术指标、对标案例 月度级

报告中所有具体数字（如"5 天 Story 周期"、"30 个 Squad"、"3-5 倍产出"）和案例（如 Anthropic、Cursor 实践）都属于当前快照下的参考实例，会随技术演进被替换。任何新出现的实践都应能通过附录 F 的"实践注册表"接入框架，无需改动正文内核。

关键论点： - 原型来源：德勤 GDC 参访（2026-05-08）观察到的"未来三角色"模型 - 哲学基础：内部市场化（蒙德拉贡/海尔/韩都衣舍）+ Workflow→Agent 渐进（Anthropic）+ 6 个共同基因（10 家公司） - 实施路径：3 阶段渐进改革（参考实例：3 个 PI，可根据组织节奏调整）

方法论说明：本报告本身由"3 人类 + 多智能体"协作生产——作者主导问题定义和判断，多个 Claude Agent 并行做研究、写作、评审。其底层协作框架借鉴了 POMASA（Pattern Language for Knowledge Engineering with LLM）的若干模式。POMASA 是给 LLM 知识工程用的模式语言，不适合直接迁移到组织设计（其 Bounded Context 是上下文窗口边界，不是组织边界；Shared Resource Pool 是向量库共享，不是人员池）。详见附录 E · 报告生产的多智能体协作过程。

第一部分 · 背景与诊断

1. 当前 ART 的问题

Porsche CCP ART 目前的结构： - 10 个 Scrum Team，每个 5-9 人 - 2-3 个 Value Stream - 传统 SAFe 节奏：双周 Sprint，10 周 PI

核心痛点： 1. 前期反复对齐：PM 写 PRD → Dev 看不懂 → 开会 → 改 PRD → 再开会 → 开发 → QA → 返工。一个 Story 从想法到上线 4-6 周。 2. 角色割裂：BA/Dev/QA/UX 各管一段，交付物在不同系统流转（Jira/Confluence/Git/测试平台）。每个人都在"翻译"。 3. AI 工具浅层使用：开发者用 Copilot 写代码，但流程没变，AI 只是更快地完成"原本就该做的事"，没有改变工作方式。 4. 管理层级冗余：SM 对齐进度，PM 对齐需求，TL 对齐技术——每一层都在消耗时间。

2. 德勤 GDC 的启示

2026-05-08 参访德勤重庆 GDC，观察到的核心实践：

BA-Pipeline + MetaForge 平台： - 业务分析 → AI 生成方案 → AI 生成代码 → AI 生成测试 → 部署 - 一个完整流程的人员配置：3 个人

Harness Master 多阶段质量治理： - 以 Big QA / SQA 思路设计端到端质量规则、过程护栏、Gate Control 与报告机制 - 将规则嵌入 Agent 的 Blueprint、Hooks、Steering 与 Skill 中，让 AI 在执行中自检、留痕、触发升级 - QA 角色从“测试执行者”升级为“质量治理者 / 过程护栏设计者”，QC、V&V 与 Tester 型执行工作主要由 AI Agent 和自动化工具链承担

外部理论验证：

《AI 软件工程范式革命》一文（参见核心数据来源）从工程史视角提出了与德勤观察高度一致的判断：

  • 闭环优先 > 单点替换：不要在 IDE 里只塞一个 Copilot，而要围绕“生成—验证—修复—沉淀规则”构造端到端 AI 产线。德勤的 BA-Pipeline + Harness Master 六阶段正是这一思路的落地实例。
  • 确定性裁判是地基：编译器、类型系统、单元测试、CI/CD、灰度监控等过去五十年留下的自动化验证基础设施，是 AI 软件工程的地基。Harness Master 的 Quality Rules + Gate Control + Toolchain 三层与此直接对应。
  • 场景驱动的隐性知识蒸馏：文章认为最难的一关是如何把专家隐性知识蒸馏出来——传统 Wiki、Confluence、流程文档的共同问题是“没有问题驱动，专家经验不会显化”。这与本框架的 Skill / Blueprint / 实践注册表设计目标一致：不是静态文档，而是“问题触发 → 规则沉淀 → Agent 复用”的闭环。

该文章同时提醒我们：Copilot 模式不是终局，但也不是弯路——它是过渡形态、训练场和数据采集层。真正的问题不是“要不要 Copilot”，而是“是否停留在 Copilot 不再往闭环演进”。这与本框架三阶段渐进路线（Assistant → Augmented → Native）的判断一致。

未来三角色模型： 1. AI Orchestrator：PO 在 AI 时代的拓展角色，负责需求理解、业务价值定义、Story 拆解、与利益相关者沟通 2. AI Engineer：纯粹的实现工程师，负责 Agent/Skill 的技术配置和构建、Prompt 工程、AI 生成代码的质量把控 3. Harness Master：SM 在 AI 时代的拓展角色——流程管理与质量治理双肩挑，负责交付节奏、流程护栏、质量原则、Guardrails、Gate Control、质量报告与对 Orchestrator 的过程约束

3. 设计原则的根本性转变

3.1 单点提效 vs 整体提效

关键认知：原子小队（Squad）解决的是局部提效——单个交付单元的产出倍增。 但整体提效——组织级的价值创造速度——的杠杆在 Value Stream / ART / Portfolio 三层。

一支高效 Squad 困在低效的 ART 流程中，依然交付不了价值； 30 支 Squad 没有 Portfolio 层的价值流对齐和资源调度，会变成 30 个孤岛。

每层的提效杠杆完全不同：

层 提效公式 主要风险
Portfolio 价值/投入比 = ∑(战略对齐的VS产出) / ∑(预算) 做错的事（再快也无意义）
ART 协同效率 = 1 / (跨 VS 等待时间 + 依赖阻塞) VS 之间互相阻塞
Value Stream 流动效率 = 价值时间 / 总周期时间（含等待） 局部最优、全局次优
Squad 单元产出 = AI 杠杆 × 团队成熟度 内卷但不出价值

核心警示： - 只优化 Squad → 局部最优，全局可能更差（Squad 跑得快但 VS 卡在审批/依赖/对齐） - 只优化 ART/Portfolio → 顶层好看，底层苦不堪言（PI 规划很顺但 Squad 无法落地） - 四层同步优化 → 真正的组织级提效

本报告后续章节中： - 第 4-5 章讲 Squad 层（局部提效） - 第 6 章讲 VS / ART 层（流动与协同提效） - 第 7 章新增 Portfolio 层（战略提效）

3.2 闭环优先 vs 单点替换 Core 内核

关键认知：AI 原生交付不是“在每个现有节点上塞一个 AI 工具”，而是围绕“生成—验证—修复—沉淀规则”构造端到端闭环。

单点替换的陷阱： - 人需求 → 人设计 → AI 编码 → 人测试 → 人部署 - AI 节点被人化接口切成孤岛，无法形成端到端 AI 主导流程 - 形成“人 → AI → 人”的不确定性循环：AI 学习人类代码也学习人类错误，人 review 标准仍是旧标准

闭环优先的路径： 1. 先建立一条端到端封闭的 AI 全流程小回路（如德勤 BA-Pipeline 的 8 步 Harness） 2. 闭环内迭代：让 AI 在有限边界内自我纠偏，沉淀 Rules / Checklist / Gate 3. 逐步开放复杂边界：从形式化程度最高的节点开始（编码 + 测试 → 发布运维 → 系统设计 → 需求分析） 4. 闭环吞并：成熟闭环逐步吸收相邻节点，扩大自治范围

与本框架的对应： - Squad 层的 5 天交付周期就是一个微型闭环：需求理解 → AI 生成 → 自动验证 → 部署 → 复盘沉淀 - Harness Master 的 Gate Control 是闭环内的确定性裁判 - 实践注册表是闭环产出的规则资产化机制

关键定位转变：

从"降本"转为"增效不降本"——不裁员，让同样的人通过 AI 实现 3-5 倍产出。这是一个增长导向、而非成本导向的转型。

但"3-5 倍产出"必须是 VS/ART/Portfolio 三层都打通之后的整体产出，而非 Squad 局部速度。否则只是把瓶颈从代码转移到流程。

├─ 测试生成 Agent 产出测试
└─ Harness Master Rules 自动验证

Day 4: 集成 + 质量门
├─ 代码审查 Agent 扫描
├─ Harness Master 多阶段质量门
└─ 部署 Agent 准备上线

Day 5: 上线 + 复盘
├─ 部署 Agent 执行
├─ 监控 Agent 跟踪
└─ 3 人 30 分钟复盘，沉淀 Skill

内核原则： - 短周期 + 高频反馈（周期长度可变，但短反馈循环不变） - AI 生成在前，人类审查在后（具体比例可演化） - 每周期必须沉淀可复用资产（Skill、Blueprint、Rules）

4.4 与 Agent 的协作模式 Core 内核

本节解决一个报告此前缺失的维度：三角色定义了"三个人类怎么分工"，但没定义"这三个人怎么跟 Agent 一起工作"，以及"Agent 之间怎么协作"。以下是原则和实操。

4.4.1 核心原则：不要把 Agent 系统设计成一家公司

很多团队在设计 Agent 系统时，会自然采用一种模式：让一个 Agent 当 PM、一个当架构师、一个当开发、一个当测试，再让它们像公司部门一样顺序交接（俗称"三省六部"架构）。

这个模式在工程上是脆弱的。原因不是"多 Agent 不好"，而是它犯了三个关键错误：

错误 1：角色标签 ≠ 专业能力

同一个模型可以写 PRD、写代码、做测试分析。给它贴上"产品经理""测试工程师"的标签，不会让它拥有真正的专业能力——只会改变它的表达风格和注意力方向。真正的专业能力来自：工具、上下文、知识源、验证标准和权限边界。一个"测试 Agent"如果不能运行测试、不能读日志、不能对照验收标准，那它只是一个用测试口吻说话的文本生成器。

错误 2：顺序交接导致上下文衰减

text
PM Agent ──摘要──→ Dev Agent ──摘要──→ QA Agent
上下文: 100%      上下文: ~40%       上下文: ~20%
设计推理全丢      设计意图丢失        只剩碎片

每次交接，传递过去的只是"结论"而非完整推理。用户的原始意图、需求背后的假设、方案取舍过程、被放弃的备选项、隐含约束——这些全部丢失。链路越长，偏移越大。最终可能出现一种危险状态：每一步局部看都合理，但整体已经偏离了最初要解决的问题。

Anthropic 在 "Building Effective Agents" 中明确建议使用简单、可组合的任务驱动模式（prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer），而非复杂的角色框架。ChatDev（ACL 2024）论文的实证数据也表明，角色化流水线的 Quality 得分仅 0.3953（0-1 量表），远未达到生产可用。

错误 3：预设步骤让 Agent 表演剧本而非推理问题

报告 §9.4 Pattern 6（去预设化指令）已指出："Long instructions, staged checklists usually backfire: the model pattern-matches your scaffolding instead of reasoning." 角色化编排是最高级别的"预设化指令"——不仅预设了步骤（需求→设计→编码→测试），还预设了每个步骤的"角色"。Agent 不再推理代码，而是在角色剧本里表演。

4.4.2 正确的 Agent 编排原则 Core 内核

原则一：一个主 Agent 持有完整意图

主 Agent 负责理解目标、维护上下文、分解任务、调度工具和子 Agent、合并结果、对最终输出负责。责任不能分散在多个角色之间消失。

原则二：子 Agent 是能力模块，不是部门员工

不要定义"你是 PM Agent / 你是测试 Agent"。要定义：

需求澄清器：识别目标、边界、验收标准 技术审查器：检查方案风险、依赖和复杂度 测试生成器：根据验收标准生成测试用例 执行器：在受控环境中修改代码并运行验证

重点不是角色名，而是：输入是什么、输出是什么、能用什么工具、不能做什么、成功标准是什么、如何验证。

原则三：所有关键状态必须外化

至少维护这些持久化文件：

text
/spec.md           # 目标、范围、非目标、验收标准
/plan.md           # 阶段计划、依赖、检查点
/decision-log.md   # 关键决策、原因、备选方案
/progress.md       # 当前进展、完成项、阻塞项、下一步
/test-log.md       # 验证记录、失败记录、修复记录

不要依赖"模型应该记得"。聊天记录不是可靠的工程状态。可靠的是显式、结构化、可审计的外部状态。

原则四：交接必须传证据，不只传结论

子 Agent 返回结果时，应包含：推荐方案 + 证据 + 假设 + 被放弃的备选方案 + 风险 + 验证方式 + 仍未解决的问题。这能显著降低后续 Agent 的误解概率。

原则五：验证 Agent 应该挑战，而不是接棒

验证 Agent 不应只是"读开发 Agent 的输出然后写测试报告"。它应独立对照原始需求、验收标准、代码变更、边界条件、日志和测试结果。它的任务不是配合，而是质疑。

4.4.3 过渡期的 Agent 协作演化 Instance 实例

上述原则（主 Agent + 能力模块 + 状态外化）是 AI Native 终态的协作模式。在达到终态之前，团队需要经历三个阶段的 Agent 协作方式演化。以下是对齐到项目计划时间线的实操方案。

text
┌─────────────────────────────────────────────────────────────┐
│  Phase 0: 个人 Agent (PI 18-19, AI 15%→40%)                │
│  • 每个人在自己的角色内独立使用 AI 工具                       │
│  • PO 用 AI 拆需求 | Dev 用 AI 做 Code Review                │
│  • 重要：SM 开始建"Agent 使用台账"——记录谁用什么 Agent        │
│    做了什么、效果如何                                        │
│  • Agent 协作模式：无──每个人和自己的 Agent 1:1               │
├─────────────────────────────────────────────────────────────┤
│  Phase 1: 共享 Agent (PI 20-21, AI 40%→60%)                │
│  • 团队开始共享同一份 feature_list.json 和 /spec.md           │
│  • Dev 和 QA 开始用同一个 Agent 实例（而非各自的 Agent）      │
│  • 开始试行 Mob Coding 节奏（Driver 轮换，见 §4.4.4）         │
│  • 关键信号：Feature Checklist 成为团队和 Agent 之间的         │
│    共享语言，不再有人"翻译"需求                               │
├─────────────────────────────────────────────────────────────┤
│  Phase 2: 团队 Agent (PI 22-23, AI 60%→85%)                │
│  • 完整 Mob Coding：单一 Agent 作为第四成员                    │
│  • 状态文件（spec/plan/decision-log/progress/test-log）       │
│    全部外化，Agent 和人类共享同一套状态                        │
│  • 子 Agent 按需调用（并行探索、对抗审查），但主 Agent 持有     │
│    完整意图和状态                                            │
└─────────────────────────────────────────────────────────────┘

Phase 0 的关键动作： - SM 建台账、观察 Agent 使用模式、识别"哪些角色之间在互相翻译需求"——这些就是未来角色合并的切入点 - 每个人建立自己的 Prompt/Skill 库 - 不做角色合并，不做 Agent 共享

Phase 1 的准入条件： - 每个角色都有 AI 工具在日常使用（100% 覆盖） - AI 使用率 ≥40% - Feature Checklist 已成为团队的共享工件 - SM 台账显示 ≥3 个"角色翻译浪费"的案例

Phase 2 的准入条件： - 至少 1 个准原子 Squad 已在 Phase 1 验证了 Mob Coding 节奏 - 状态外化文件（spec/plan/decision-log/progress/test-log）已成为团队日常 - 团队成员不再说"我的 Agent"，而说"我们的 Agent"

4.4.4 Mob Coding：AI Native 阶段的日常工作模式 Instance 实例

在 Phase 2（AI Native），三人原子团队采用 Mob Coding 模式——三个人轮流驱动同一个 Agent，Agent 作为第四团队成员持续在场。

驾驶轮换规则：

阶段 Driver Solution Lead (Nav) AI Engineer (Nav) Harness Master (Nav)
需求拆解 Solution Lead — 技术可行性 验收标准完整性
实现 AI Engineer 业务意图校准 — 质量规则触发
质量验证 Harness Master 价值确认 技术审查 —
复盘沉淀 轮流 轮流 轮流 轮流

Navigator 规则：发现问题时先记录到 parking lot（共享文档），不打断 Driver 与 Agent 的对话。Driver 完成当前交互后再处理 parking lot——这避免了"七嘴八舌打断 Agent 上下文"。

典型一天的 Mob Coding 节奏：

text
09:30  Mob Standup (5 min)
       └─ 三人 + Agent 一起看 feature_list.json，选今天 1 个 Story

09:35  Solution Lead 做 Driver (20-30 min)
       └─ "Agent，这是今天的 Story，帮我细化验收标准，追问边界条件"
       └─ AI Engineer (Nav)：parking lot 记"需要先做数据迁移"
       └─ Harness Master (Nav)：parking lot 记"补充空数据场景"

10:00  AI Engineer 做 Driver (60-90 min)
       └─ "Agent，基于验收标准开始实现"
       └─ Solution Lead (Nav)："这个交互和用户预期不一致"→ parking lot
       └─ Harness Master (Nav)："覆盖率不能低于上次基线"→ parking lot

11:30  Agent 自主运行 (30 min)
       └─ 三人可短暂离场或处理 parking lot
       └─ Agent 自己跑端到端验证（Pattern 10）

14:00  Harness Master 做 Driver (30-45 min)
       └─ "Agent，跑完整端到端验证。有失败按 Pattern 12 自己修，3 次上限"

15:00  三人 Code Review + parking lot 清理 (20 min)

16:00  Harness Master 做 Driver (15 min) — 清洁交接
       └─ git commit + 更新 feature_list + progress note

什么时候不适用 Mob Coding：

场景 替代方案
两个完全独立的 Story 可并行 分叉——AI Engineer 独立驱动 Agent 做 Story A，Solution Lead 用 Agent 做 Story B 需求分析
Agent 跑长任务（部署、大规模测试） Agent 后台运行，三人处理 parking lot 或 Skill 沉淀
简单确定性任务（格式化、依赖更新） AI Engineer 直接指令，不需要 Mob

5. 三角色定位 Core 内核

三角色的分工逻辑是框架内核——需求与价值、技术实现、质量治理的三元结构。 各角色的具体能力构成和典型工作流是当前实例，随工具演进会变化。

关键澄清：三角色不是凭空新造，而是PO、Dev、SM 铁三角在 AI 时代的极简版。

传统 Scrum 的基本细胞是 PO（定义方向）+ Dev（实现）+ SM（保障流程）。AI 原生交付中，这个铁三角的职责被重新分配： - PO → AI Orchestrator：需求与价值定义不变，工具从文档/会议升级为 Agent 编排 - Dev → AI Engineer：工程实现不变，方式从手写代码升级为 Agent/Skill 构建 - SM → Harness Master：流程保障不变，范围从“移除人的障碍”扩展到“移除 Agent 的障碍 + 质量护栏双肩挑”

技能基底依然来自 PO、Dev、SM/QA 三类专业人员，只是工作方式被 AI 放大，职责边界被重塑。

5.1 AI Orchestrator（PO 的 AI 拓展）

Core 角色本质（内核）：

AI Orchestrator 是 PO（Product Owner）在 AI 时代的拓展，不是新造一个"AI 编排官"。 其根本依然是"理解业务、定义价值、对齐需求"，但工具从文档/会议升级为 Agent 编排。

Core 核心职责（内核）： - 业务理解与利益相关者沟通（PO 的根本能力） - 需求拆解、用户故事编写、验收标准定义 - 用 AI Agent 加速需求分析、原型生成、用户访谈整理 - 编排 Agent 流程，让需求快速转化为可验证产物 - 价值优先级判断、Sprint Backlog 决策

Instance 能力模型（当前实例）： - 70% 业务/产品/需求能力 / 20% AI 工具使用 / 10% 基础技术理解 - 来源：现有的 PO、产品经理、BA、需求分析师 - 不需要：成为技术专家，但需要能用 AI 编排流程 - 类比：从"写 PRD 的产品经理"升级为"用 AI 把需求快速变成可验证原型的产品经理"

Instance 典型一天（当前实例）： - 9:00-9:30：与利益相关者对齐当周优先级 - 9:30-12:00：用 AI 拆解需求 → 生成用户故事 → 评审验收标准 - 14:00-16:00：审查 AI 产出的需求分析、原型、设计文档 - 16:00-17:00：与 Stakeholder 演示进展、收集反馈

5.2 AI Engineer（实现工程师）

Core 角色本质（内核）：

AI Engineer 是纯粹聚焦于实现的工程师——做 Agent 配置、Skill 构建、Prompt 工程、工具集成。 不是"懂AI的资深架构师"，而是"用 AI 工具高效构建系统的实现者"。

Core 核心职责（内核）： - Agent 的设计、配置、调试与优化 - Skill 模块的构建与复用 - Prompt 工程、Tool 集成、模型/工具选型 - AI 生成代码的审查、重构、质量把控 - 技术债务与重构

Instance 能力模型（当前实例）： - 70% 工程实现能力 / 20% AI/Prompt 工程 / 10% 系统集成 - 来源：现有的 Dev、全栈工程师 - 不需要：做模型研究、不需要懂深度学习理论 - 类比：从"自己写每一行代码的开发"升级为"用 AI 高效构建可靠系统的实现工程师"

Instance 典型一天（当前实例）： - 9:30-12:00：配置/调试 Agent，优化 Prompt 和 Tool - 14:00-16:00：审查 AI 生成的代码，重构关键模块 - 16:00-17:30：构建/迭代可复用 Skill，集成新工具

5.3 Harness Master（流程+质量治理 / SM 的 AI 拓展）

Core 角色本质（内核）：

Harness Master 是 SM（Scrum Master）在 AI 时代的拓展角色——核心不是“更会排 Jira 看板的人”，而是流程管理者 + 质量治理者双肩挑。

在传统 Scrum 中，SM 负责流程顺畅、移除障碍、引导团队持续改进；QA/SQA 负责质量体系、测试策略、缺陷预防。在 AI 原生交付中，这两条线的边界被 AI 消解了—— - 流程障碍不再是“人找不到人或等审批”，而是“Agent 之间的交接断裂、上下文丢失、工具链卡住” - 质量问题不再是“测试没覆盖”，而是“Agent 产出验证不足、Gate 规则过时、技能沉淀失效”

Harness Master 同时看管流动效率（Flow）和质量结果（Quality）——流程让价值快速流动，质量让流动的结果可信任。这也是为什么这个角色不能叫“SM”（与 Value Stream Lead 的角色层级冲突），也不能叫“QA”（窄化了流程管理的职责）。

Harness Master 的双重职责：

维度 流程管理（SM 的进化） 质量治理（QA/SQA 的进化）
关注点 Squad 的交付节奏是否顺畅？障碍是否被移除？ Agent 产出是否达标？质量门是否有效？
主要问题 流程是否让正确结果稳定发生？ 产物是否通过验证且有追溯？
AI 时代变化 流程障碍从“人等人”变成“Agent-Agent 交接断裂”——需要设计 Agent 间协作护栏 QC/V&V 型执行由 AI Agent 承担——人转向原则定义、门禁设计、异常升级判断
典型动作 维护 Feature Checklist 进度、确保每日清洁交接、发现流程反模式、组织复盘 设计 Quality Rules + Gate Control + Toolchain、维护三类裁判系统、Risk Left Shift
类比 流程教练 + 交付管家 质量 PMO + 护栏设计师

Core 核心职责（内核）：

流程管理： - 维护 Squad 的交付节奏（5 天周期），确保 Day 1 初始化 → Day 2-5 增量执行的节奏不被打破 - 确保每周期清洁交接（git commit + progress note），让任何人/Agent 接手时能 5 分钟恢复上下文 - 识别并移除流程障碍——无论是“人等审批”还是“Agent 上下文丢失” - 组织每周期复盘，推动从“这次出问题了”到“Skill/Blueprint 更新防止下次再出”的闭环 - 维护 Feature Checklist 的完整性和真实性——“Done”必须是端到端验证通过的，不能自欺欺人 - 管理外部依赖——当 Squad 需要 VS 内其他 Squad 或平台团队的配合时，主动对接消除阻塞

质量治理： - 设计端到端质量治理体系：Quality Rules、Gate Control、Toolchain、Reporting - 将 Guardrails 写入 Agent Blueprint、Hooks、Steering 与 Skill，约束 AI Orchestrator 和 AI Engineer 的工作边界 - 定义每个阶段的 Checklist / Gate / Review，决定哪些门禁必须通过，哪些审查可以按风险触发 - 维护过程合规、审计留痕、追溯链路与质量报告 - 识别系统性质量风险和流程反模式，推动 Smart Review、Risk Left Shift 与资产沉淀

三类裁判系统（流程+质量的理论基础）：

Harness Master 设计的质量门不是单一维度，而是分层递阶的三类裁判协同：

类型 典型机制 作用 在 Harness 中的对应
确定性裁判 编译器、类型系统、单元测试、契约校验、lint、ArchUnit、SpotBugs 判断硬错误——通过/不通过 Toolchain + Gate Control
统计性裁判 监控指标、A/B 测试、异常率、性能趋势、周期时间、流动效率、用户行为数据 判断运行质量+流程健康度——趋势/异常 Reporting + Quality Dashboard
专家性裁判 架构评审、价值取舍、风险接受、伦理判断、业务意图校准 判断复杂权衡——需人介入 Review（按风险触发）+ 人工升级

关键原则： - 确定性裁判应尽可能自动化，成为 AI Agent 的默认行为 - 统计性裁判需要 Harness Master 设计监控基线和异常阈值（同时覆盖质量指标和流程指标） - 专家性裁判保留给人的判断力，Harness Master 决定何时触发人工介入 - 不能把所有判断都交给确定性裁判——需求是否有价值、架构是否长期可维护、流程瓶颈是否已消除、异常场景是否遗漏，这些没有简单的通过/不通过标准

Instance 能力模型（当前实例）： - 30% 流程管理与敏捷教练能力 / 25% SQA / 质量体系 / 合规治理 / 20% 测试工程与质量风险经验 / 15% AI 工具与自动化理解 / 10% 技术基础（能看代码、能读 Agent 日志） - 来源：现有 SM、敏捷教练、QA Lead、质量工程师、SQA、测试架构师、具备流程治理经验的 Dev Lead - 不等同于：手动测试执行者、纯粹的流程协调员、或传统“只排看板不碰质量”的 SM - 关键能力跃迁：从“确保 Sprint 顺利”升级为“确保 Squad 的 AI 交付系统稳定地产出高质量结果”——同时看管流动和质量两条线

Instance 典型一天（当前实例）： - 9:30-10:00：检查昨日交付节奏——周期时间是否偏离基线？Agent 交接是否有断裂？Feature Checklist 推进是否正常？ - 10:00-11:00：审查 Agent 执行报告、Gate 通过率、异常升级记录和追溯链路；识别流程反模式（如“连续 3 个 Story 在 Day 4 才发现问题”） - 11:00-12:00：与 AI Orchestrator 同步需求优先级和外部依赖阻塞，与 AI Engineer 同步技术障碍 - 14:00-15:30：更新质量规则、流程护栏、交接模板；设计新的 Gate 或 Checklist 应对新发现的风险 - 15:30-17:00：沉淀可复用资产——Checklist、Gate、Review 模板、复盘记录；推动跨 Squad 复用

6. ART 整体架构（VS / ART 层 — 流动与协同提效）

Core 内核：分层结构（ART → VS → Squad → Agent）+ 决策小组治理 + 共享平台 + 端到端价值流 Instance 实例：本章所有具体数字均为当前组织规模下的参考配置，需根据实际情况调整。

本章的重点不是"如何拆 Squad"，而是 VS 和 ART 这两层如何把 N 个 Squad 的局部提效转化为组织级整体提效。

6.0 整体提效的两大杠杆

杠杆 1：流动效率（Value Stream 层） - 衡量：价值时间 / 总周期时间（含等待、依赖、审批） - 优化方向：消灭等待——一个 Story 从想法到上线，有多少时间在"动"，多少时间在"等" - 典型问题：Squad 5 天写完代码，但上线要等 3 周（其他 VS 的审批/集成测试/合规审查）

杠杆 2：协同效率（ART 层） - 衡量：1 / (跨 VS 等待时间 + 依赖阻塞次数) - 优化方向：消灭依赖——VS 间应该高内聚低耦合，不应互相阻塞 - 典型问题：30 个 Squad 都依赖同一个平台团队，平台成为全组织瓶颈

6.2 Value Stream 重组（流动提效核心） Core 内核 + Instance 实例

6.2.1 VS 设计的内核原则 Core

端到端价值流（End-to-End Value Stream）： - 每个 VS 应该是完整的端到端价值交付路径——从客户需求到客户价值实现 - VS 内部高内聚（包含从需求到运维的全链路） - VS 之间低耦合（最小化跨 VS 依赖）

业务结果度量，非活动度量： - ❌ "VS 本月交付了多少 Story"（活动度量，没意义） - OK "VS 本月给客户/业务带来了多少价值"（如 NPS 提升、转化率提升、成本下降）

Value Stream 自治原则： - VS 内的 Squad 应能在 VS 内部自主决策、自主交付，不依赖外部审批 - VS 有自己的目标（OKR）、自己的预算、自己的优先级

机制 目的 实现方式

跨 VS Skill 流动 让单个 VS 的经验扩散到全 ART Skill 注册表跨 VS 共享，定期跨 VS 演示

6.5 共享平台（Platform Team） Core 内核

Squad 不应自己搭建 Agent 基础设施、CI/CD、监控、数据平台——这些应由共享平台团队提供。

平台团队的本质：把"组织级提效工具"做成产品，让所有 Squad / VS 都能消费。

Instance 当前平台组成（实例）： - AI Platform：Agent 基础设施、模型服务、Prompt 库、Skill 注册表 - DevOps Platform：CI/CD、自动化部署、监控告警 - Data Platform：数据总线、ETL、特征工程 - Security Platform：身份、密钥、合规扫描

平台团队自己也是 Squad 结构（3 人 + N Agent），但服务对象是其他 Squad 而非业务方。

6.6 专家池（Expert Pool） Core 内核

Core 功能：提供共享专业能力，避免每个 Squad 都配齐所有专家。

Instance 典型组成（当前实例）： - UX Designers：跨 Squad 设计支持 - Security/Compliance Specialists：安全/合规审查 - Data Engineers：数据管道 - Domain Experts：业务领域专家 - AI Architects：跨 Squad 的 AI 架构指导

Core 协作模式：嵌入式（Embedded），不是工单式（Ticket-based）。专家进入 Squad 工作一段时间，然后回池。具体周期可由 Squad 协商。

6.7 VS / ART 层提效的反模式 Risk

以下是常见错误，需明确避免：

反模式 表现 后果
微观管理 三人决策小组干预 Squad 内部决策 Squad 失去自主性，提效失败
VS 假自治 名义上 VS 自治，实际所有决策仍需上级批 VS Lead 变成传声筒
活动度量 用 Story 数、代码行数衡量 VS 鼓励内卷而非价值
跨 VS 频繁开会 用会议解决依赖 协作成本爆炸
平台后置 让 Squad 自己搭基础设施 重复造轮子，N 个 Squad N 套工具
临时对齐文化 每次跨 VS 协作都要"对齐一下" 接口契约缺失，依赖于人

7. Portfolio 层（战略提效与价值流投资组合）

Core 内核：Portfolio 是组织级提效的最高杠杆点——决定"做什么最有价值"。 ART 层解决"如何把事做对"，Portfolio 层解决"做对的事"。

关键洞察：再好的 Squad、再顺畅的 VS，如果做的事本身价值低，整体提效都是假的。 AI 时代的 Portfolio 治理变得更关键——AI 让"做事的成本"急剧下降，意味着"做错事的机会成本"急剧上升。

7.1 为什么 Portfolio 层是最大杠杆

传统视角：Portfolio 层是"高层规划"，离一线很远，慢且僵化。

AI 时代的反转： - AI 让 Squad 交付速度从月级降到周级 - 决策周期不变（季度级）→ 决策成为新瓶颈 - 做错一个 Epic 的成本 = 30 个 Squad × 一个 PI 的产出

Portfolio 不再是"战略文件夹"，而是实时的价值流投资组合管理系统。

7.2 Portfolio 层的核心机制 Core 内核

7.2.1 价值流投资组合（VS Investment Portfolio）

把 N 个 VS 视为投资组合，按"价值/投入"比例动态分配资源。

核心问题： - 哪些 VS 在增长（投入应增加）？ - 哪些 VS 在衰退（投入应减少或退出）？ - 哪些新机会值得新建 VS？

7.2.2 Lean Budget & Guardrails Core 内核

放弃"项目预算"模式，采用"价值流持续预算 + 护栏"。

传统模式（已过时）： - 项目立项 → 申请预算 → 按预算执行 → 验收 - 问题：AI 时代变化太快，立项时的假设半年就过时

Lean Budget 模式： - 每个 VS 有持续滚动的预算（按季度调整） - Portfolio 不审批每个 Epic，只设"护栏"（如安全、合规、技术标准） - VS 在护栏内自主决策投资方向

护栏示例： - 🛡️ 任何 VS 不得做违反数据合规的项目 - 🛡️ 任何 VS 不得绕过共享平台另起炉灶 - 🛡️ 任何 VS 的单 Epic 预算不超过总预算的 X%

7.2.3 战略主题与 OKR 对齐 Core 内核

Portfolio 通过"战略主题"对齐所有 VS，而不是通过审批每个项目。

机制： - Portfolio 层每季度发布 3-5 个"战略主题"（如"提升经销商数字化体验"、"AI 原生交付转型"） - 每个 VS 根据战略主题制定自己的 OKR - Portfolio 只检查 OKR 是否与战略主题对齐，不检查具体活动

好处： - 一线 VS 自主决定如何实现战略，不受微观干预 - 战略变化时只改主题，VS 自己调整

7.2.4 跨 VS / 跨 ART 资源调度 Core 内核

Portfolio 是组织内"流动资源"的最高调度者。

调度对象： - 人员（专家池 / 核心骨干的跨 VS 流动） - 预算（VS 间的预算重分配） - AI 能力（共享 Agent / Skill 的优先级） - 数据（跨 VS 数据共享的策略）

机制： - 季度资源再分配会议（不是每个项目单独审批） - 紧急情况的"快速重组通道"（48h 内可临时调动资源）

这就是"整体提效"——四层协同，价值快速流动，资源动态调整。

9.4 Anthropic 生产实践模式（2026-05 更新）Instance 实例

来源：本小节基于 Anthropic 公开 GitHub 仓库（anthropics/skills、anthropics/claude-code、anthropics/defending-code-reference-harness）及其工程博客《Equipping agents for the real world with Agent Skills》8 的公开信息整理。 性质：这些是 Anthropic 当前产品的内部工程实践，不是组织设计模板，但其模式可直接映射到 Squad 层的 Agent 配置、Skill 开发和质量验证流程。

模式 1：渐进式披露架构（Progressive Disclosure）

来源：anthropics/skills 仓库的 skill-creator/SKILL.md1

核心机制：

text
┌─────────────────────────────────────────────────────────────┐
│  Level 1: Metadata (name + description)                     │
│  • 始终常驻上下文 (~100 词)                                   │
│  • 决定 Skill 何时触发                                        │
├─────────────────────────────────────────────────────────────┤
│  Level 2: SKILL.md body                                     │
│  • Skill 触发时加载 (<500 行)                                │
│  • 核心工作流、决策树、最佳实践                                 │
├─────────────────────────────────────────────────────────────┤
│  Level 3: Bundled Resources                                 │
│  • 按需加载，无容量限制                                       │
│  • scripts/ (黑盒可执行脚本)                                  │
│  • references/ (领域参考文档)                                 │
│  • assets/ (模板、字体、图标等)                               │
└─────────────────────────────────────────────────────────────┘

对 Squad 层的启发： - Skill 设计不是"写得越多越好"——核心指令控制在 500 行以内，超过则分层 - 参考文件按领域隔离——多技术栈支持时，references/ 按变体分离（如 aws.md / gcp.md / azure.md），避免一次性加载无关内容 - 脚本作为黑盒——复杂、确定性、重复性任务封装为脚本，通过 --help 暴露接口后直接调用，不加载到 LLM 上下文（见 webapp-testing SKILL.md2 的 scripts/with_server.py 设计）

模式 2：评估驱动开发（Eval-Driven Development）

来源：anthropics/skills 仓库的 skill-creator/SKILL.md1

核心循环：

text
捕获意图 → 访谈研究 → 编写 SKILL.md → 创建测试用例
    ↓
并行运行 (with-skill vs baseline)
    ↓
定量断言评分 + 用户定性反馈
    ↓
基于反馈重写 Skill → 扩大测试集 → 重复

关键实践： 1. A/B 对比必须同时启动：with-skill 和 baseline（无 skill 或旧版本 skill）的测试运行必须在同一轮次并行启动，避免时间偏差 2. 定量 + 定性双轨： - 定量：pass rate、执行时间、token 消耗（mean ± stddev） - 定性：用户在浏览器 viewer 中逐条审阅输出，留下文字反馈 3. 评估问题设计原则（来自 mcp-builder SKILL.md3）： - Independent（互不依赖） - Read-only（非破坏性） - Complex（需要多步工具调用） - Realistic（基于真实人类用例） - Verifiable（有明确可验证的答案） - Stable（答案不会随时间变化）

对 Harness Master 的启发： - Skill 本身也需要质量门——不是写一次就永久有效，而是通过 eval 循环持续验证 - "非歧视性断言"检查：如果某个断言无论 skill 是否存在都总是通过，则该断言无价值，需剔除

模式 3：侦察-行动分离（Reconnaissance-Then-Action）

来源： - defending-code-reference-harness README4 的 "Map the system before you scan it" - webapp-testing SKILL.md2 的 "Reconnaissance-Then-Action Pattern"

核心原则：

Don't prescribe how to hunt; give context and step away.

在漏洞检测管道中的体现：

text
Step 1 (Day 1): 交互式侦察
  ├─ /threat-model bootstrap → 建立威胁模型
  ├─ /vuln-scan → 静态扫描
  ├─ /triage → 人工验证、去重、分级
  └─ 产出：THREAT_MODEL.md, TRIAGE.json

Step 2 (Day 2+): 自动化行动
  ├─ recon → 轻量 agent 读源码，划分 focus_areas（7 个独立子系统）
  ├─ run → N 个并行 find-agent，各自从不同 focus_area 出发
  ├─ verify → 独立 grade-agent 在清洁容器中验证每个崩溃
  └─ report → 可执行见证（crash trace）优于文字论证

对 Squad 层的启发： - 任何复杂任务都先分区再并行： recon 阶段把搜索空间切分，避免多个 agent 堆在同一个浅层 bug 上 - 验证器是承重墙（load-bearing component）：廉价程序化门控（sanitizer signal, reproduces 3/3）+ 对抗性评分 agent，优先消除假阳性 - 交互式启动，自动化放大：Day 1 人工引导建立上下文和基线，Day 2+ 管道自主运行

模式 4：管道化自主执行（Pipelined Autonomous Execution）

来源：defending-code-reference-harness4 的 harness/ 管道设计

管道结构：

text
recon → find → verify → report → patch
  ↑      ↑       ↑        ↑       ↑
  │      │       │        │       └─ 独立验证阶梯：apply→build→PoC stop→regression pass→re-attack
  │      │       │        └─ 可执行见证优先于文字报告
  │      │       └─ 清洁容器中独立验证（finder 从未触碰过的环境）
  │      └─ 并行 agent，按 recon 分区各自独立搜索
  └─ 轻量映射，生成 focus_areas 列表

关键设计： 1. 两容器信任边界：finder 运行在隔离容器中，verifier 在另一个从未被 finder 触碰过的容器中运行 2. gVisor 沙箱：自主 agent 执行目标代码时，必须在 gVisor 沙箱内运行，出站流量限制到 API 调用 3. 验证阶梯（Verification Ladder）：patch 后的 diff 必须经过可执行验证——原始 PoC 是否停止触发、回归测试是否仍通过、重新攻击 patched binary 是否失败

对 Harness Master 的启发： - 确定性裁判（编译、单测）+ 统计性裁判（reproduces 3/3）+ 专家性裁判（独立 agent 评审）的三层验证，在 Anthropic 的管道中是物理隔离的，而非逻辑隔离 - 最深层结果来自"执行-观察-迭代"循环：给 agent 一个可运行的环境（HTTP 流量、日志、种子数据库），让它 chaining findings 而非止步于静态报告

模式 5：交互式 Skill + 自动化管道混合（Interactive + Automated Hybrid）

来源：defending-code-reference-harness4 的 Day 1-2 分工设计

分层： | 阶段 | 模式 | 安全边界 | 人工介入 | |------|------|---------|---------| | Day 1 | 交互式 Skill (/quickstart, /threat-model, /vuln-scan, /triage) | 只读写文件，每次工具使用需人工批准 | 高 | | Day 2+ | 自动化管道 (bin/vp-sandboxed run) | gVisor 容器隔离，agent 必须在沙箱内 | 低（只在 triage/patch 时介入）|

对 Squad 层的启发： - 不是所有任务都适合"全自动"——新任务或高风险任务从交互式开始，成熟后管道化 - Skill 设计应支持两种模式：交互式（人工批准每一步）和自主式（在护栏内自主运行） - 安全边界随自动化程度提升而增强：从"人工批准"到"沙箱隔离"

模式 6：去预设化指令（De-prescriptive Instructions）

来源：defending-code-reference-harness README4 的 Best Practices

核心原则：

Long instructions, staged checklists, and piles of reference material usually backfire: the model pattern-matches your scaffolding instead of reasoning about the code.

实践： - 给 agent "目标 + 工具 + 上下文"，而不是 "步骤 1-10 的详细清单" - 让 agent 自己选择路径——它经常以人类研究者想不到的方式找到漏洞 - 用威胁模型（threat model）划定边界，而非用检查列表规定动作

对 AI Orchestrator 的启发： - AI Orchestrator 的职责是"定义目标、提供上下文、划定边界"，而非"编排每一步动作" - 过度编排会让 agent 模式匹配脚手架，而非真正推理——这与本框架中"AI 生成在前，人类审查在后"的内核一致

模式 7：环境初始化-增量执行分离（Setup-Execution Split）

来源：Anthropic 长时运行 Agent 研究5

核心机制： Anthropic 发现，让一个 Agent 从零开始一次性完成大型任务（如"克隆 claude.ai"），几乎必然失败——Agent 要么试图一次做太多导致上下文溢出，要么看到已有进展就提前宣布完成。解决方案是把工作拆成两个截然不同的阶段：

text
┌─────────────────────────────────────────────────────────────┐
│  Session 1: 初始化器（Initializer）                          │
│  • 只做环境搭建，不做功能开发                                  │
│  • 产出：init.sh（一键启动开发环境）                           │
│  • 产出：feature_list.json（200+ 条可验证特性，初始全部 ❌）  │
│  • 产出：初始 git commit                                     │
├─────────────────────────────────────────────────────────────┤
│  Session 2-N: 执行器（Coding Agent）                         │
│  • 每次会话只做一件事：选一个未完成的 feature，实现它          │
│  • 启动流程固定：读 git log → 读 progress file → 跑冒烟测试   │
│  • 结束流程固定：git commit → 写 progress note → 标记 feature │
└─────────────────────────────────────────────────────────────┘

关键发现： - Anthropic 试过让同一个 Agent 既搭建环境又写功能——Agent 倾向于在搭建环境时就试图"顺便"实现核心功能，结果做到一半上下文溢出，下一个 session 拿到的是一个半成品+无文档的环境 - 把"初始化"和"执行"强制分离后，Agent 在后续 session 中每次都能快速恢复上下文并稳定产出

对 Squad 层的落地指导： - Day 1 是"初始化日"，不是"开发日"：AI Orchestrator 把需求拆成可验证的特性清单（不是 PRD 段落），AI Engineer 搭建项目骨架和开发环境脚本，Harness Master 定义验收标准 - Day 2-5 是"增量执行日"：每天只聚焦一个 Story，做完一个再开下一个，不并行 - 特性清单是团队共享的"完成定义"：Orchestrator 写清单，Engineer 实现，QA 验证——三方看的是同一份清单，消灭"我觉得做完了"的模糊空间

模式 8：特性清单驱动进度追踪（Feature-List-Driven Tracking）

来源：Anthropic 长时运行 Agent 研究5

核心机制： Anthropic 用一份结构化的 JSON 文件作为 AI Agent 和人类共享的进度视图。关键设计决策：

设计选择 理由
用 JSON 而非 Markdown Agent 更不容易"顺手"修改或覆盖 JSON 文件
200+ 条细粒度特性 不是 10 条大功能，而是"新建聊天按钮创建新对话""回车键发送消息"级别
初始全部标记 "passes": false 不给 Agent "已经差不多了"的错觉
Agent 只能改 passes 字段 严禁删除或修改特性描述——防止 Agent 降低标准
每条特性包含验证步骤 不是"登录功能正常"，而是 5 步可执行验证

特性条目示例：

json
{
  "category": "functional",
  "description": "用户点击'新建聊天'按钮后创建空白对话",
  "steps": [
    "导航到主界面",
    "点击'新建聊天'按钮",
    "验证新对话已创建",
    "验证聊天区域显示欢迎状态",
    "验证对话出现在侧边栏"
  ],
  "passes": false
}

对 Squad 层的落地指导： - 用结构化特性清单取代"PRD + 口头对齐"：AI Orchestrator 产出特性清单（JSON/YAML），每条可独立验证 - Harness Master 负责清单完整性：不是等开发完再测，而是在 Day 1 就参与清单评审——"这些验收步骤够不够？要不要加边界场景？" - Daily 站会看清单而非"口头汇报"：今天改了哪几条从 ❌ → OK？没过的为什么？

模式 9：会话间清洁交接（Clean-State Handoff）

来源：Anthropic 长时运行 Agent 研究5

核心机制： Anthropic 发现 Agent 在多 session 工作中最大的效率杀手不是模型能力，而是上下文恢复成本——每个新 session 要从零理解"项目现在是什么状态"。他们的解决方案来自观察优秀人类工程师的日常工作习惯：

text
每个 Session 结束时（Clean Exit）:
  ├─ git commit（含清晰的 commit message）
  ├─ 更新 claude-progress.txt（本次做了什么、下一步建议做什么）
  └─ 确保代码处于"可直接合并到 main"的状态（无已知 bug）

下个 Session 启动时（Quick Recovery）:
  ├─ git log --oneline -20（了解最近做了什么）
  ├─ 读 claude-progress.txt（了解进度和下一步）
  ├─ 运行 init.sh 启动开发服务器
  └─ 跑一遍基础冒烟测试（确保环境没有被上次遗留的 bug 破坏）

关键发现： - 没有清洁交接时，Agent 平均要花 20-30% 的 session 时间恢复上下文——读文件、猜状态、修复被上一个 session 遗留 bug 破坏的环境 - 有了清洁交接后，恢复时间降到 <5%，Agent 几乎立即进入生产状态

对 Squad 层的落地指导： - 每周期复盘不只是"聊聊"，而是"清洁交接"：git commit message 写清楚，Skill 更新记录写清楚，让下一个周期（或接手的人/Agent）能 5 分钟内恢复上下文 - "可合并到 main 的状态"是硬约束：每天结束时代码必须编译通过+冒烟测试通过，不允许"明天再修" - Harness Master 维护一份 init.sh 级别的环境恢复脚本：确保任何人（或 Agent）接手时能一键拉起完整开发环境

模式 10：一次一件事 + 端到端自验证（One-at-a-Time + E2E Self-Verification）

来源：Anthropic 长时运行 Agent 研究5

核心机制： Anthropic 发现 Agent 最常见的质量失败模式不是"代码写错了"，而是"功能标记为完成但没有真正端到端验证"。Agent 倾向于跑完单元测试就标记 passing，但实际上功能在浏览器里根本不可用。

解决方案： - 一次只做一个 feature：不允许 Agent 同时推进多个功能——分散注意力导致每个都做不彻底 - 必须用真实用户路径验证：给 Agent 配备浏览器自动化工具（如 Puppeteer MCP），让它像真实用户一样操作应用来验证 - 验证失败 → 修复 → 再验证 → 才标记 passing：不是"测试挂了就标记 known issue"，而是修复到通过

text
实现 feature → 单元测试通过
        ↓
启动开发服务器 → 浏览器自动化验证端到端流程
        ↓
     ┌─ 通过 → 标记 passing → 进入下一个 feature
     └─ 失败 → 修复 → 重新验证（循环直到通过）

关键发现： - 不给 Agent 浏览器自动化工具时，Agent 标记为"完成"的功能中，约 30-40% 端到端不可用 - 给了浏览器自动化工具并明确要求端到端验证后，这个比例降到 <5%

对 Squad 层的落地指导： - "Done"的定义必须是"端到端验证通过"，不是"代码写完了"：AI Engineer 提交代码前必须跑端到端验证（集成测试 / E2E 测试 / 手动点击验证） - Harness Master 不给"感觉差不多"放行：质量门的通过条件必须是可自动验证的断言，而非主观判断 - 每天只聚焦一个 Story：不在多个 Story 之间切换——5 天周期 = 5 个 Story，每天一个

模式 11：分级操作信任边界（Tiered Trust Boundary）

来源：Anthropic Claude Code auto mode 设计6

核心机制： Anthropic 在 Claude Code 的 auto mode 中将 AI 的操作权限分成三级，不是"全部审批"或"全部放行"的二元选择，而是按风险分级：

text
Tier 1: 内置安全白名单 → 自动放行，不经过分类器
  ├─ 文件读取、文本搜索、代码导航
  ├─ Todo 管理、Plan 模式切换
  └─ 用户配置的 always-allow 规则（如"允许运行代码格式化工具"）

Tier 2: 项目内文件操作 → 自动放行，不经过分类器
  ├─ 项目目录内的文件写入和编辑
  └─ 可通过版本控制回溯，风险可控

Tier 3: 分类器审核 → 只有高风险操作才触发
  ├─ Shell 命令、网络请求、外部工具集成
  ├─ 项目目录外的文件系统操作
  └─ 子 Agent 的启动和返回

关键设计理念： - 用户在实际使用中批准了 93% 的人工审批弹窗——意味着大部分审批是形式化的，真正需要人判断的只有少数高风险操作 - 分级后，99.6% 的日常操作自动放行（Tier 1+2），只有 0.4% 的操作触发审核（Tier 3）

对 Squad 层的落地指导： - Harness Master 的质量门也应分级，不是每个 check 都要人工审批： - L1 自动门（编译、lint、单测、类型检查）→ AI Agent 自动通过 - L2 统计门（测试覆盖率趋势、性能指标波动）→ 异常时通知 Harness Master - L3 人工门（架构评审、安全审查、UX 验收）→ 按风险触发 - 不要让 Harness Master 变成"审批瓶颈"：如果 93% 的审批都是形式化的，那把 Harness Master 的人力集中在真正需要判断的 7%

模式 12：拒绝-重试而非中断（Deny-and-Continue）

来源：Anthropic Claude Code auto mode 设计6

核心机制： 当 AI Agent 的操作被安全分类器拦截时，Anthropic 的设计不是"停止会话、弹出审批窗口、等待人工介入"，而是：

text
Agent 发起操作 → 分类器判断
    ├─ 安全 → 放行，Agent 继续
    └─ 危险 → 拒绝 + 返回拒绝理由
                ↓
         Agent 收到拒绝理由 → 自行寻找更安全的替代路径
                ↓
         ┌─ 找到替代方案 → 继续工作（会话不中断）
         └─ 再次被拒 → 继续尝试（最多连续 3 次 / 累计 20 次）
                └─ 达到上限 → 停止 + 升级到人工

关键设计理念： - 0.4% 的误拦率看似很低，但如果每次误拦都中断会话，对长时任务就是灾难 - "拒绝-重试"让误拦只消耗一次重试，不影响整体进度 - 连续拒绝上限（3 次连续 / 20 次累计）是安全阀——防止 Agent 陷入死循环或用各种变体绕过限制

对 Squad 层的落地指导： - 质量门失败不应直接抛给人：AI Agent 应先尝试自动修复，只有在反复失败时才升级到 Harness Master 或 AI Engineer - Harness Master 设计质量门时，每个门都应附带"失败时的建议修复方向"：不给 Agent 只返回"❌ 不通过"，而是"❌ 不通过：测试覆盖率 72%，目标 80%——建议补充 src/auth/ 和 src/payment/ 模块的测试" - 设定自动重试上限：避免 Agent 在"修复-失败-修复"中无限循环——建议默认上限 3 次，超过则标记为 blocked 并通知人类

13.6 这一章本身的"内核"

即使本章描述的注册表机制、阶段流程、模板格式都可能演化，其底层哲学是稳定的：

任何足够长寿命的框架，都必须把"什么变"与"什么不变"显式分开。

内核解决"组织如何在 AI 时代有效运转"——这是慢变量； 扩展点解决"今天用哪个工具、哪个模式、哪个案例"——这是快变量。

把两者混在一起，框架要么三个月过时，要么寸步难行。

第六部分 · 评审与落地校准

14. Stakeholder 评审包

目标不是一次性批准完整重组，而是先对齐“是否值得进入 Pilot 验证”。评审应聚焦四层假设，而不是讨论某个 Squad 的组织细节。

14.1 评审对象与核心问题

Stakeholder 最关心的问题 需要给出的判断

Business Owner 是否真的更快产生客户/业务价值？ 是否愿意提供试点场景和反馈窗口
RTE / ART 管理者 是否破坏现有 PI 节奏？ 是否接受渐进式双轨运行
VS Lead / PO / BA 角色是否被削弱或替代？ 是否接受 AI Orchestrator 是现有 PO 能力升级
Dev / TL / Architect 技术质量和架构一致性如何保证？ 是否认可 AI Engineer + Platform 的质量边界
QA Lead / SQA / SM SM 和 QA 是否被误解？ 是否认可 Harness Master 是 SM+QA 在 AI 时代的融合角色——流程管理+质量治理双肩挑，而非传统 tester 或看板协调员的替代称呼

14.3 评审必须避免的三类偏差

  1. 把 Pilot 讨论成组织大重组：Phase 1 只验证一个场景，不改变全 ART 组织结构。
  2. 只讨论工具，不讨论价值流：工具选型属于实例层，评审重点是四层假设是否成立。
  3. 把 AI 原生误读成裁员叙事：本框架的硬约束是增效不降本、不裁员。

15. Pilot 选择评分卡

Pilot 场景要满足两个条件：一是足够真实，能证明价值；二是足够可控，不会把组织风险一次性放大。

维度 权重 高分特征 低分特征
业务价值 25% 与当前战略主题直接相关，业务方愿意快速反馈 只是内部效率优化，业务价值难衡量
端到端可交付性 20% 可在一个 VS 内闭环交付，依赖少 跨多个 VS / 外部系统依赖重
需求可拆解性 15% 可拆成多个小 Story，适合短周期验证 需求高度不确定或需要长期探索
技术风险可控 15% 架构边界清晰，有测试环境和回滚路径 涉及核心交易链路、合规高风险
数据与质量可观测 10% Cycle Time、缺陷、业务结果可度量 数据缺失，结果只能靠主观判断
团队意愿 10% PO/Dev/QA 均愿意参与并承担反馈 团队抗拒，Pilot 会变成额外负担
复用潜力 5% 产出的 Skill / Blueprint 可扩散到其他 Squad 一次性特殊场景，难以复用

推荐门槛：总分 ≥ 75 分进入 Pilot；60-74 分需要补齐前置条件；< 60 分不建议作为 Phase 1。

15.1 推荐优先级

  1. 优先选择一个高价值但中等复杂度的 VS 内场景：能证明端到端流动提效。
  2. 避免第一个 Pilot 选择跨 VS 强依赖场景：否则会把 ART/Portfolio 层未成熟问题误判为 Squad 模型失败。
  3. 避免纯技术重构场景：容易证明开发效率，但难证明业务价值。

E. 报告生产的多智能体协作过程

本附录解释 POMASA 在本报告生产过程中扮演的角色——它是"如何用多个 Claude Agent 协作写出这份报告"的框架，而不是"如何设计 Porsche ART 组织"的框架。这一区分至关重要，避免领域错配。

E.1 为什么 POMASA 不适合做组织设计参考

POMASA 是 Anthropic 等团队总结的、面向 LLM 知识工程系统的模式语言。其 20 个模式都是围绕"如何让 LLM Agent 群体可靠地完成知识工作"设计的。直接迁移到人类组织设计会产生概念错配：

POMASA 原意（LLM 工程语境） 误用为组织设计时的错配
Bounded Context = LLM 的上下文窗口边界（token 限制） 误读为"组织边界"或"领域边界"（DDD 概念）
Shared Resource Pool = 向量库/工具/Prompt 库的共享 误读为"人员专家池"
Hierarchical Composition = LLM 调用链的层级编排 误读为"组织汇报层级"
Faithful Blueprint = Prompt 模板的忠实实例化 误读为"组织角色定义模板"
Multi-Layer Validation = LLM 输出的多层校验 误读为"人工质量门"

这些误读会让组织设计建议显得有理论支撑但实际是循环论证——拿 LLM 工程模式套到组织上，再用"符合 POMASA"反向论证组织设计的正确性。这是方法论错误。

13.5 隐性知识蒸馏：实践注册表的核心挑战

理论参考：《AI 软件工程范式革命》将“场景驱动的隐性知识蒸馏”列为 AI 产线最大的瓶颈。

问题：传统 Wiki、Confluence、流程文档、ISO 文档的共同缺陷是——没有问题驱动，专家脑子里的经验直觉不会显化。文档越写越厚，Agent 越用越蠢。

解法——问题驱动的 Skill 沉淀闭环：

text
Agent 执行出错 / 产出不达标
        ↓
专家介入纠正（不是改代码，是改规则/约束/上下文）
        ↓
Harness Master 提取：这次纠正的本质是什么？
        ↓
写入 Skill / Blueprint / Checklist / Steering
        ↓
下一个同类任务 → Agent 自动应用新规则
        ↓
验证是否解决 → 若未解决，继续迭代

关键设计： - 不是“先写文档再让 AI 学”，而是“AI 先犯错 → 人纠正 → 规则即时沉淀” - 每个 Skill 条目必须绑定一个真实触发场景（Scenario），而不是抽象最佳实践 - Harness Master 负责审核提取的规则是否具有通用性，避免过度拟合个别案例 - 实践注册表中的每个 Practice 都应包含 trigger_scenario 字段——说明什么情况下会触发这条规则

四个推进方向： 1. 让 AI 主动问“我为什么被纠正了”——Agent 在收到纠正时自动生成追问，帮助专家显化判断依据 2. AI 跟随专家工作并主动观察提问——类似“学徒模式”，Agent 在旁边观察专家处理例外，记录决策模式 3. 建立场景化知识库格式——每个知识点必须包含：触发条件、正确做法、常见错误、反例、责任人 4. AI 主动构造极端案例反向逼问专家——用对抗生成的方式，逼出专家未曾显化过的边界判断 5. 让 Agent 自己创建和迭代 Skill——Anthropic 在 Agent Skills 文章中明确将"Agent 自己创建、编辑、评估 Skill"列为未来方向7。这对应本框架中"问题驱动的 Skill 沉淀闭环"的终极形态：Agent 不再只是 Skill 的消费者，而是 Skill 的生产者和迭代者——出错 → 自我诊断 → 更新规则 → 下次自动应用
